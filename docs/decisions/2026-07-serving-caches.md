# 服务端缓存与检索热路径优化决策

## 背景

- `readIndex` 每个请求都重新读盘并 `JSON.parse` 整个 `data/index.json`。
  索引内嵌全部向量，体积可达几十 MB，解析耗时数百毫秒且制造大量 GC 压力，
  问答、检索、状态接口和服务端页面全部受影响。
- `searchIndex` 每次查询为所有分块重建词元集合、词频表、小写全文和向量模长，
  BM25 文档频率用 `Array.includes` 线性扫描，检索延迟随语料量线性恶化。
- 每条聊天消息都要为查询向量支付一次远程 Embedding 往返（数百毫秒 + 配额），
  即使是重复问题。
- 同步时向量批量生成是"全有或全无"：中途遇到配额错误会丢弃已完成的所有批次。
- 分块边界窗口 `max(start + 400, idealEnd - 240)` 在 430 的块大小下退化为
  30 字符，超长章节几乎总被硬切在句子中间（遗留自更大的块配置）。

## 决策

- `store.ts` 按文件指纹（mtime + size + inode）缓存解析后的索引对象，
  `writeIndex` 写入后同步刷新缓存；返回对象跨请求共享，约定只读。
- `search.ts` 以 `chunks` 数组身份为键，用 `WeakMap` 缓存检索派生数据
  （词元 Set、词频 Map、小写全文/标题、向量模长、平均长度、文档首块映射）。
  打分公式与阈值完全不变，既有排序语义逐位保持。
- 查询向量按「提供方|模型|原文」做 128 条 LRU 缓存；文档向量不进缓存，
  失败不缓存。
- 同步逐批生成向量，失败保留已完成前缀并记录进度化告警；
  复用旧索引分块时总是拷贝，避免原地改写共享缓存对象。
- 分块边界窗口改为「至少填充 60% 且回退不超过 240 字符」，
  并接受换行、！、？作为切分边界；仅影响此后新同步或变更的文档。
- 数据目录支持 `KNOWLEDGE_DATA_DIR` 覆盖，供测试与部署迁移使用。

## 未采用方案

- 重排融合改用 RRF 等新算法：现有确定性融合与证据门槛是刻意决策且有测试锚定，
  在没有评测集的情况下变更排序语义属于无度量的风险。
- 检索结果整体缓存：Embedding 暂时失败会把降级策略钉在缓存里；
  查询向量缓存 + 派生数据缓存已覆盖主要延迟，收益不值得引入失效复杂度。
- 倒排索引裁剪候选集：会改变 exactContent 兜底路径的召回语义；
  派生缓存已把每次查询的成本降到可接受水平。

## 风险与缓解

- 共享索引对象被调用方原地修改：已审查全部调用点（组件、路由、reports、
  resources 均为只读或新建数组），`sync` 中唯一的原地赋值改为先拷贝。
- 指纹碰撞导致读到旧缓存：指纹含 inode，`writeIndex` 的临时文件重命名
  会产生新 inode；进程内写入还会直接刷新缓存，不依赖指纹。
- 查询向量缓存放大坏向量影响：仅缓存成功响应，容量 128 条，
  换模型或提供方后键自动失效。

## 回滚

- 回滚本次提交即可恢复逐请求解析与逐查询重算，无数据迁移。
- 索引文件格式未变化；分块边界变化只影响回滚后新同步的文档。
